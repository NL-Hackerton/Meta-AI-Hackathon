# 수용 기준·제품 품질 평가·구현 순서 계획

상태: 계획만 작성했다. **제품 AC 통과 0건, BA·PQ 판정 0건, 평가 데이터 확보 0건, T00~T16은 원본대로 TODO.** 이 문서는 테스트·평가 실행 결과가 아니다. BA 기준, PQ 기준, 평가 데이터 계획, 일정 재배치는 각각 SC-001~010과 SC-011~013이 승인된 뒤에 적용하는 제안이다. 루트 `SPEC.md`와 `TASKS.md`의 정의·상태·목표일은 바꾸지 않는다.

2026-10-24 결정에 따라 고객 인터뷰, 실점포 확보, 매출·CTR 개선은 착수·완료 gate가 아니다. 그 대신 직접 만져 확인할 수 있는 제품 완결성을 내부 품질 gate로 판정한다. 이 gate는 시장 수요나 광고 성과를 입증하지 않으며, 그러한 주장에도 사용하지 않는다. 제품 기능·권한·실호출 gate(H1~H4, LIVE-OK)는 그대로 유지한다.

## 0. 표기와 증거 구분

| 표기 | 의미 | 완료 증거로 쓸 수 있는 범위 |
| --- | --- | --- |
| `fixture` | 외부 호출 없이 고정 입력·Mock 응답으로 실행 | 로컬 처리, 상태 전이, 경계 계산. 실제 provider 동작은 증명하지 않음 |
| `live` | 해당 실행 시점에 실제 provider/Marketing API를 호출 | provider 계약과 실제 결과. 요청 시각, 모델 ID, sanitized 요청·응답 metadata를 함께 기록 |
| `replay` | 과거 `live` 응답의 sanitized snapshot을 다시 입력 | 저장된 모델 출력의 재채점·재현. 새 live 완료로 계산하지 않으며 원 capture 시각을 표시 |
| `[필수]` | 안전·무결성 불변식에서 나온 이진 판정 | 한 건이라도 실패하면 해당 기준 불통과 |
| `[제안 목표, 미실측]` | 내부 품질 목표로 제안한 수치 | 아직 측정하지 않았다. 공식 심사 배점·입상 확률·광고 성과 예측으로 쓰지 않음 |
| 자동 판정 | 기하·시간·해시·기록으로 계산 가능한 판정 | 픽셀 실현 가능성, 포함률, 동기화 오차, digest 일치 등 |
| 사람 판정 | 내부 검토자가 source와 결과를 보고 내리는 판정 | 관찰 문장과 영상 장면의 일치, 실제 화면 가독성. 고객 검증이 아니다 |

픽셀 실현 가능성(제품 bbox와 여백이 crop 크기 안에 들어갈 수 있는가)은 참조 라벨과 기하 계산으로 자동 판정한다. 반면 source evidence가 해당 문장을 실제로 뒷받침하는지는 사람이 검토한다. source link가 존재한다는 사실은 진실성이나 법적 적합성을 보증하지 않는다(SC-012).

## 3. 평가 데이터 계획 [제안: SC-013]

### 3.1 구성

총 12개 미디어 사례를 쓴다. 합성 8개는 경계 조건을 통제하고, 실물 4개는 실제 촬영 조건을 확인한다. 실물 영상은 팀이 직접 촬영했거나 광고 사용이 허용된 적법 라이선스 자산이어야 하며, 고객·점포 영상은 필요조건이 아니다. **현재 12개 모두 미확보·미라벨·미평가 상태다.**

| 사례 | 분할 | 출처 | 의도한 경계 조건 |
| --- | --- | --- | --- |
| S1 | 개발 | 합성 | 1920×1080 이동 제품, 1.5초 완전 가림(invisible) 후 재등장 |
| S2 | 개발 | 합성 | 9:16에서 여백 포함 수용이 불가능한 폭 800px 제품, 비슷한 크기의 방해 object 2개(다중 SAM ID) |
| S3 | 개발 | 합성 | 회전 metadata MOV, VFR, 약 40초 길이(28초 초과 선택), 알려진 offset에 배치한 직접 녹음 한국어 음성 clip 3개 |
| S4 | 개발 | 합성 | 3초 짧은 입력, 무음. note에는 팀이 정한 가격·할인만 명시한다(explicit 근거). 근거 없는 효능·성능 주장은 note에 넣지 않고 §3.4의 adversarial 편집 시나리오로 따로 주입한다 |
| S5~S8 | 평가(frozen) | 합성 | S1~S4와 같은 조건 범주를 다른 seed·속도·색·가림 위치·음성 offset·문구로 생성. S8도 S4와 같이 note에는 가격·할인만 명시하고 근거 없는 주장은 §3.4로 분리 |
| R1 | 개발 | 직접 촬영/라이선스 실물 | 생활용품 1종을 손으로 들고 회전, 한국어 설명 음성, 실내 조명, 휴대폰 세로 MOV |

| R3 | 평가(frozen) | 직접 촬영/라이선스 실물 | R1 조건 범주, 다른 제품·장소·촬영 세션 |
| R4 | 평가(frozen) | 직접 촬영/라이선스 실물 | R2 조건 범주, 다른 제품·장소·촬영 세션 |

개발 6개는 합성 4개와 실물 2개, frozen 평가 6개는 합성 4개와 실물 2개다. 실물 사례마다 촬영자 또는 라이선스 문서, 광고 사용 범위, 등장 인물 동의, 제3자 음악·상표 노출 여부를 권리 기록으로 남긴다. 권리 기록이 없는 영상은 평가와 live 게시에 쓰지 않는다. 실물 note의 가격·할인 등은 팀이 정한 실제 값만 쓴다.

### 3.2 참조 라벨

참조 라벨은 source만 보고 만들며, 해당 사례에 파이프라인을 실행하기 전에 확정한다.

- 제품 위치: 0.5초 간격 keyframe의 제품 bbox와 상태(`visible`, `partial`, `invisible`). 평가는 라벨된 keyframe에서만 계산하고 그 사실을 보고한다.
- 대상 object: 초기 대상이 무엇인지 사람의 라벨. SAM ID와의 대응은 실행 후 기록한다.
- 음성 구간: 원본 오디오의 발화 시작·끝(10ms 단위)과 전사 문장.
- 주장 목록: note의 explicit 가격·할인 span과 위험 분류. §3.4에서 주입할 adversarial 문구와 위험 분류도 실행 전에 확정하고 hash한다.
- 합성 사례는 생성 parameter에서 bbox·가림 구간·음성 offset의 정답을 얻는다. 생성 parameter 파일도 hash 대상이다.

### 3.3 누수 방지와 freeze 절차

1. 평가 사례는 확보 즉시 원본 파일·note·권리 기록·참조 라벨·생성 parameter의 SHA-256을 `eval manifest`에 기록한다. 저장 위치는 `data/` 하위로 하고, 원본 미디어를 repo에 commit할지는 권리 범위를 확인한 뒤 정한다.
2. 프롬프트, 정책 규칙, `MAX_STEP_PX`, 폰트 크기, timeline 규칙 등의 조정은 개발 6개로만 한다. 평가 사례는 개발 중 provider에 보내지 않고, 참조 라벨은 애플리케이션이 읽는 경로에 두지 않는다.
3. 평가 실행 직전 code commit, 모델 ID, 프롬프트·정책 규칙·폰트 hash, `ffmpeg -version`, 설정 상수를 `run manifest`로 고정한다. 실행 전에 eval manifest hash를 다시 대조한다. 불일치하면 평가를 시작하지 않는다.
4. 평가 6개 전체를 `live`로 한 번 실행한다. 이 실행은 입력→분석→추적→보강→렌더→`AWAITING_APPROVAL`까지이며 자동 승인·자동 게시를 하지 않는다. 모든 provider 응답은 sanitized model-output snapshot으로 저장하고, 채점과 재채점은 이 snapshot의 `replay`로 수행한다. 모델 재호출 결과는 같은 실험으로 섞지 않는다(BA-18).
5. 실제 광고 게시는 실행 전에 지정한 실물 평가 사례 R3의 revision 1개만 대상으로 한다. 운영자가 UI에서 검토·승인한 뒤 9:16 A/B 광고 2개를 PAUSED로 게시한다. R3가 승인 조건을 충족하지 못해 R4로 바꾸면 그 사유를 보고서에 남긴다. 합성 사례, §3.4 adversarial 주입 revision, 승인 차단 상태의 revision은 실제 광고 계정에 게시하지 않으며, 이들의 게시 차단·결합 동작은 fixture Mock으로만 검증한다.
6. 6개 사례 × 비율별 A/B 6개 = 36개 결과와 단계별 실패를 모두 보고한다. 재시도는 새 시도로 기록하되 첫 시도를 삭제하지 않으며, 가장 좋은 시도만 고르는 best-of-N을 금지한다.
7. 평가 후 결함을 고쳤다면 새 version으로 같은 6개를 다시 평가하고 두 결과를 함께 보고한다. 이때 평가 세트는 이미 관찰된 상태이므로 엄밀한 held-out 결과라고 표기하지 않는다.

### 3.4 adversarial 주장 주입 시나리오

S4(개발)와 S8(평가)에서 live 생성이 끝난 뒤, 운영자가 UI 편집으로 근거 없는 효능·성능 주장을 훅 또는 카피에 넣는다. 주입 문구는 §3.2에서 미리 확정한 것만 쓴다. 이 문구는 운영자가 넣은 것이며 모델이 생성한 주장으로 보고하지 않는다. 기대 결과는 해당 revision의 승인 차단이다. 모델이 스스로 생성한 고위험 주장은 이와 별도로 집계한다. 주입 revision은 실제 게시 대상이 될 수 없다.

## 5. 실제 provider 증명 요구

최종 완료에는 아래 `live` 증거가 모두 필요하다. 하나라도 없으면 fixture·replay 결과가 있어도 완료로 판정하지 않는다.

| 대상 | 필요한 live 증거 | 대체로 인정하지 않는 것 |

| Spark | 평가 사례의 구조화 응답과 schema 검증 결과 | Mock 응답, 수기 작성 JSON |

각 증거에는 실행 시각, 모델·Graph 버전, 요청 수, sanitized 응답 metadata, 연결된 job·revision을 기록한다. 비밀값과 원본 고객 데이터는 증거 파일에 넣지 않는다.

## 6. 범위 보존 구현 순서 [제안: SC-013]

`[가정]` 10일은 킥오프 2026-10-26(D1)부터 2026-11-04(D10)까지다. 제출 마감 2026-11-05 11:00 KST와 제출 행위는 H4의 사람 작업이다. 루트 TASKS의 선행 관계·목표일은 바꾸지 않으며, 아래는 승인 시 적용할 실행 순서 제안이다. 새로운 story 상태표를 만들지 않고, 실행 상태는 기존 TASKS.md 한 곳에만 기록한다. `stories.yaml`은 checkpoint 판단을 받기 전 생성하지 않는다.

마지막 2일(D9·D10)은 기능 추가가 아니라 검증·재현·복구에 쓴다. 최종 범위는 그대로 유지한다: 원본 영상 6개(3비율×A/B), 실제 PAUSED 광고 2개, Spark·SAM·Image·Voice live 경로, CLI, 웹 전과정, CAP-9. H2·H3는 기능 통합보다 먼저 해제를 시도하고, 해제되지 않으면 관련 태스크를 BLOCKED로 기록한다.

일정이 밀려도 범위를 몰래 줄이지 않는다. 다음 경우는 “완료”가 아니라 **미완료**로 보고한다.

- H2 또는 H3가 해제되지 않아 §5의 live 증거가 하나라도 없는 경우
- 실제 PAUSED 광고 2개의 생성·read-back이 없는 경우
- 웹 전과정을 실제 브라우저로 수행하지 못한 경우
- 6개 중 일부 비율·훅만 렌더된 경우, Image가 대체 카드로만 동작한 경우, CLI 또는 웹 한쪽만 동작하는 경우
- PQ의 `[필수]` 항목이 하나라도 실패한 경우

이 경우에도 fixture·replay 시연은 할 수 있으나, 화면과 보고서에 모드를 표시하고 live 완료를 대신한다고 말하지 않는다. `[제안 목표, 미실측]` 미달은 숨기지 않고 측정값과 함께 보고하며, 목표 수치를 사후에 바꾸지 않는다.

## 7. 데모 실행 검증 checklist

대본·대사는 이 문서에서 작성하지 않는다. 아래는 시연 전에 실행 가능 여부만 확인하는 항목이다.

- [ ] 깨끗한 설치 절차로 준비한 환경에서 서버와 CLI가 시작된다.
- [ ] 사용할 실물 영상의 권리 기록과 eval manifest hash가 일치한다.
- [ ] 화면의 모든 산출물에 fixture/live/replay 표시가 보이고, replay에는 원 capture 시각이 보인다.
- [ ] 원본과 비율별 결과를 나란히 볼 수 있고 degraded·clipped·Image 대체 표시가 숨겨지지 않는다.
- [ ] source reference 클릭 시 원본 timestamp 또는 note span으로 이동한다.
- [ ] 제한 편집 후 revision이 바뀌고 이전 승인이 무효화된다.
- [ ] 정책 block 또는 근거 없는 고위험 주장이 있으면 승인 버튼이 비활성화되고 이유가 보인다.
- [ ] 승인 후 별도 publish 동작이 필요하다.
- [ ] 게시 대상 revision이 지정 실물 평가 revision이며 합성 사례나 adversarial 주입 revision이 아니다.
- [ ] 테스트 광고 계정에서 PAUSED 광고 2개와 소재를 read-back으로 대조할 수 있다.
- [ ] 키 제거 시 live가 명시적 오류를 내고 fixture 성공으로 바뀌지 않는다.
- [ ] 네트워크 장애 시 사용할 replay 경로가 준비되어 있고, live 결과로 표시되지 않는다.

## 8. 해제 순서와 남은 선택

1. **구현 계약 승인:** SC-001~010 중 모순·안전 경계(001~005)를 먼저 검토하고, SC-011~013(웹 전과정, source-linked 제한 편집, 내부 품질 gate)을 함께 판단한다. 사람 검토 없이 root SPEC/TASKS를 수정하지 않는다.
2. **제품 결정:** 데모 제품과 직접 촬영 또는 라이선스 자산, 광고 목적·destination, 운영 환경·비용 한도·키 담당을 정한다. 고객 확보나 고객 동의 영상은 선행 조건이 아니다. 원본 §9의 사람 결정 항목은 유지한다.
3. **문서 근거:** API 확인 장부와 OSS 후보를 바탕으로 허용 모델·외부 코드·폰트·광고 규격을 확인한다. 공식 규정이 없으면 임의의 심사 배점이나 입상 확률을 만들지 않으며, PQ 목표를 그 대용으로 쓰지 않는다.
4. **실행 게이트:** H2/H3는 문서 조사로 통과하지 않는다. 권한 있는 환경에서 승인된 호출과 계정 결과를 확인해야 한다.

현재 구현 착수 전에 필요한 것은 root 계약의 모순 정리와 SC-011~013 승인 여부다. 기본 offline 검증, 내부 품질 평가, 최종 live 완료는 서로 분리해 판정하며, 셋 다 같은 T00~T16 순서에 매핑한다.
