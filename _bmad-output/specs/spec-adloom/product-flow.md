# 사용자 흐름과 상호작용 기준

근거: 루트 `SPEC.md` §1·3·4·6·9와 `.memlog.md`의 2026-10-24 결정(SC-011·012·013, CAP-9). 이 문서는 **interaction brief**다. 화면 배치·색·글꼴·컴포넌트 모양을 정하지 않고, 사용자가 보는 정보·할 수 있는 행동·상태 전이만 정한다. 시각 시안이나 프로토타입은 없고 렌더 화면 검증 전이다.

`[제안]`이 붙은 항목은 SC 승인 전 구현 계약이 아니다. 루트 명세의 "웹은 승인·미리보기 전용"(§1, §2)은 SC-011이 승인될 때까지 유효하다. CAP-1~8, 영상 6개(3비율×훅 A/B), 실제 PAUSED 광고 2개, Spark/SAM/Image/Voice 경로, CLI는 그대로 유지한다.

## 1. 대상과 완결 기준

- **처음 여는 심사자:** 설명 없이 페이지를 열고 저장된 작업 또는 새 작업으로 원본 확인부터 결과 내보내기까지 따라갈 수 있어야 한다.
- **로컬 운영자:** 영상과 설명을 넣고, 결과의 근거를 확인하고, 제한된 범위에서 고치고, 같은 revision을 승인·게시한다. 키 설정·실패 복구도 이 사람이 맡는다. 한 사람이 두 역할을 함께 맡을 수 있다.
- **입력 가정:** 직접 촬영했거나 적법하게 라이선스한 일반 생활용품 1개의 3~45초 영상과 200자 이하 설명. 실제 고객 영상·고객 인터뷰는 이 흐름의 전제가 아니다. [SC-013]

완결 경로는 다음 다섯 가지를 한 페이지에서 끊김 없이 확인할 수 있을 때 성립한다.

1. 결과의 각 장면이 원본 영상의 어느 시점에서 왔는지 재생하며 대조할 수 있다.
2. 카피·훅·자막의 주장마다 근거(설명 문구 범위 또는 영상 시점)와 근거 종류를 볼 수 있다.
3. 대상 물체·구간·문구를 정해진 범위 안에서 고치고, 무엇이 다시 만들어지는지 적용 전에 안다.
4. 현재 revision의 결과 6개는 승인 전에도 내려받을 수 있다. 실제 PAUSED 게시만 승인된 그 revision의 내용으로 한다.
5. 성공·경고·실패·결과 불명을 구분해 보고, 데모용 fixture/replay와 실제 live 결과를 혼동하지 않는다.

## 2. 페이지 구조

FastAPI 단일 HTML 페이지 하나에 세 단계를 둔다. 단계는 별도 앱이나 마법사가 아니라 같은 job의 같은 상태를 보는 구역이다. CLI와 웹은 같은 job·revision·승인·게시 서비스를 사용한다. [SC-011]

| 메인 단계 | 목적 | 열리는 조건 |
| --- | --- | --- |
| 1. 만들기 | 입력 등록, 실행 모드 확인, 단계 진행·취소·재개 | 항상 |
| 2. 검토·수정 | 원본 대응 재생, 근거 확인, 물체·구간·문구 수정, 6개 미리보기 | 최초 렌더 6개가 모두 commit된 뒤. 그 전에는 진행 상황만 표시 |
| 3. 승인·내보내기 | 승인, 다운로드, PAUSED 게시, 게시 결과 확인 | 현재 revision이 `AWAITING_APPROVAL` 이상일 때. 막힌 이유는 항상 표시 |

항상 보이는 작업 머리글:

- job ID, 현재 revision, 루트 상태값(`CREATED`…`PUBLISHED_PAUSED`/`FAILED`), 마지막 갱신 시각
- 실행 모드: `fixture`(녹화 응답·mock 게시), `live`(이번 실행의 실제 호출), `replay`(이전 live 결과 snapshot 재생, 기록 시각 포함)
- 승인 상태: 없음 / 현재 revision 승인됨 / 이전 revision 승인(무효)
- 미적용 편집 있음(dirty), 이전 revision 결과 표시 중(stale) 표시
- provider 준비 상태: Spark·SAM·Image·Voice·Marketing 각각 설정됨/없음/사람 gate 미승인. 키 값과 토큰은 표시하지 않는다.

첫 진입(작업 없음)에서는 "새 작업 만들기"와 "저장된 작업 열기"만 제공한다. 저장된 작업 목록은 `data/jobs/` 아래의 로컬 job이며 각 항목에 모드와 상태를 표시한다. 둘러보기 투어나 샘플 홍보 문구는 두지 않는다.

## 3. 단계 1 — 만들기

| 입력 | 처리 |
| --- | --- |
| 영상 1개(mp4/mov, 3~45초) | 업로드 직후 길이·형식·회전 정보를 로컬에서 검사한다. 부적합하면 외부 호출 없이 이유를 표시한다(AC-01). |
| 설명 텍스트(200자 이하) 또는 음성 파일 | 음성은 Voice로 전사한 뒤 텍스트로 확정하기 전에 보여 준다(AC-02). 전사본이 이후 근거 인용의 기준 문서가 된다. |
| 지역(자유 텍스트, 예: 남양주), 타기팅 국가 KR, 언어, 일 예산·통화, destination URL | 자유 텍스트 지역은 원본 계약대로 기록만 하며 타기팅 값이 아니다. 타기팅 국가는 KR로 고정한다. live 게시에 필요한 값은 게시 단계에서 다시 검사한다. 미확정 objective 등 [미확인] 값은 사용자가 고르는 척 꾸미지 않는다. |

- 실행 시작은 명시적 버튼(POST)으로만 한다. `[제안]` 서버는 202와 job ID를 즉시 돌려주고, CLI와 같은 Python pipeline을 로컬 단일 worker(동시 실행 1개)에서 실행한다. 화면은 job manifest를 polling해 상태를 갱신한다. 외부 작업 큐는 두지 않는다. worker가 다른 작업을 실행 중이면 새 실행 요청을 거부하고, 실행 중인 작업을 여는 경로를 보여 준다. 대기열이나 "대기 중" 상태는 만들지 않는다. [SC-011]
- 진행 표시는 루트 단계명(이해→추적→보강→조립) 단위로, 각 단계의 시작·완료·경고·실패와 소요 시간을 보인다. 진행률 백분율은 실측 근거가 없으면 표시하지 않는다.
- **키 없음:** live 모드에서 필요한 provider 자격이 없으면 해당 단계 실행 버튼을 비활성화하고 `E_API_AUTH` 성격의 이유를 보인다. fixture로 조용히 대체하지 않는다(AC-21, BA-15). Marketing 자격이 없어도 모델 단계와 렌더는 진행할 수 있고, 게시만 막는다. [SC-008]
- **실행 제어 상태:** 실행 제어는 `run_state`(`IDLE`/`RUNNING`/`CANCEL_REQUESTED`/`INTERRUPTED`)로 표시하며 루트 사업 상태(`CREATED`…`PUBLISHED_PAUSED`/`FAILED`)와 따로 보여 준다(implementation-contracts §6). [SC-011]
- **취소:** 취소 요청을 받으면 `run_state=CANCEL_REQUESTED`로 바뀌고 화면은 "취소 요청됨 — 현재 단계가 끝나면 멈춤"을 표시한다. 현재 단계가 정상적으로 끝나면 검증된 산출물과 사업 상태를 commit한 뒤 다음 단계를 시작하지 않고 멈춘다(`IDLE`). 진행 중인 원격 호출을 즉시 중단한다고 보장하지 않는다. renderer는 자체 ffmpeg process를 종료할 수 있지만 partial output은 commit하지 않는다. 원격에서 확정된 ID는 취소 중에도 반드시 journal에 남긴다. [SC-005·011]
- **실패·재개:** 실패 카드에는 실패 단계, 안전한 오류 요약, 마지막 성공 상태, "이 단계부터 재실행"을 둔다. 재개는 입력 digest가 같을 때만 그 단계를 다시 실행한다(BA-13). 앱이 다시 시작될 때 살아 있지 않은 worker의 `RUNNING`은 `INTERRUPTED`로 표시하고, 이미 확정된 산출물은 지우지 않으며 같은 재개 경로를 쓴다.
- 반복 schema 실패(`E_API_SCHEMA`), 추적 저품질(`degraded`), Image 실패 대체(`warnings`)는 각각 실패/경고로 구분해 표시한다. 경고는 진행을 막지 않지만 검토 단계에 그대로 따라간다.

## 4. 단계 2 — 검토·수정

### 4.1 원본·결과 대응 재생

- 결과 플레이어(선택한 1개 변형)와 원본 플레이어를 함께 둔다. 결과를 재생하면 원본이 대응 시점으로 따라간다. 대응은 `TimelineSpan`의 반개구간 변환으로 계산한다. [SC-006]
- 결과 시점에서 "원본에서 보기"를 누르면 원본이 해당 source 시점으로 seek하고, 그 구간이 원본의 어디에서 잘렸는지 표시한다.
- 원본이 반복된 구간에는 반복 번호를 표시한다. 원본 영상 위에 훅·자막 같은 문자 overlay가 겹친 구간은 base 영상의 source seek를 그대로 유지하고, overlay의 출처(문구 ID, 렌더 layer)를 따로 표시한다. "원본 영상 없음"은 원본 프레임을 쓰지 않는 엔드카드 구간에만 표시하고, 카드의 배경 출처(Image 또는 단색)를 함께 보인다. [SC-007]
- 원본 위에 현재 선택된 물체 box와 비율별 crop 영역을 겹쳐 볼 수 있다. 보간 프레임과 실제 SAM box 프레임을 구분한다.

### 4.2 근거 패널 [SC-012, CAP-9]

훅·본문·제목·CTA 표시 문구·자막·주요 장면 각각에 근거 목록을 붙인다.

| 근거 종류 | 의미 | 연결 대상 | 클릭 동작 |
| --- | --- | --- | --- |
| explicit | 사용자가 설명에 직접 쓴 주장. 사실이라는 보증이 아니다 | note의 정확한 문자 범위(quote + span) | 설명 원문에서 해당 범위를 강조 |
| observation | 영상에서 보이거나 들린다고 판단한 내용 | asset digest + timestamp(또는 구간) | 원본을 해당 시점으로 seek |
| inference | 모델이 만든 표현. 주관적·창작 문구 포함 | 근거 후보가 있으면 위와 같이 연결. 주관적·창작 문구에 억지로 근거 링크를 요구하지 않음 | 근거가 있을 때만 이동 |

- 근거가 있다는 사실은 주장이 참이거나 법적으로 적합하다는 보증이 아니다. 패널 머리에 이 문장을 고정한다.
- 서버는 존재하지 않는 note 범위, quote 불일치, asset digest 불일치, 영상 길이 밖 timestamp를 근거로 받지 않는다. 거부된 근거는 "유효하지 않은 근거"로 남기고 해당 문구를 근거 없음으로 취급한다.
- **고위험 주장:** 가격·할인·성능·효능처럼 검증이 필요한 주장으로 규칙이 분류한 문구는 explicit 근거가 없으면 생성 결과에 넣지 않는다. 사용자 편집으로 들어오면 승인을 막는다. 해제 방법은 둘뿐이다: 문구 삭제, 또는 설명에 해당 주장을 명시 입력한 뒤 재검사. 명시 입력해도 외부 사실 검증이 끝난 것이 아니라 사용자가 제공한 주장으로 남는다. 분류 규칙은 검사 도구이지 Meta 광고 심사 결과의 예측이 아니다.
- **검토 상태:** 각 주장은 `ClaimReview`로 관리하며 `pending`/`accepted`/`rejected` 중 하나다. 사실형 주장(explicit·observation)과 고위험 주장은 사람 검토가 필수다. 사람은 원본을 보고 accepted 또는 rejected를 고른다. 모델은 근거를 제안할 수 있지만 accepted를 설정할 수 없고, 근거가 있다는 이유만으로 pending이 accepted로 바뀌지 않는다. 검토 필수 주장이 하나라도 pending이나 rejected이면 승인을 막는다. rejected 주장은 문구를 삭제·수정해 새 revision에서 다시 검토한다. 주관적·창작 inference 문구는 inference로 표시해 사람이 보게 하되 근거 링크를 강제하지 않는다. [SC-012]
- 사실형·고위험 문구를 inference로 라벨만 바꾸어 검토나 차단을 우회할 수 없다. 순수 주관적·창작 inference는 최종 승인에서 검토하며 개별 accepted를 강제하지 않는다.
- observation 근거는 사용자가 원본을 보고 확인하는 대상이다. 시스템은 관찰 내용이 맞다고 판정하지 않는다.
- 근거 분류, 정책 flag, rewrite 제안, 주요 장면 선택은 모델 또는 로컬 규칙의 판단이다. 화면 문구에서 이를 "사실 확인됨", "검증 완료", "Meta 정책 승인"으로 표현하지 않는다.

### 4.3 대상 물체 후보 선택

- SAM이 반환한 object ID별로 최초 검출 프레임의 box 썸네일, 검출 프레임 수, 보간 전 coverage를 보여 준다. 기본 선택은 기존 규칙(최초 검출 프레임 최대 면적, 동률 최소 ID)이며 "자동 선택"으로 표시한다. [SC-009·012]
- 사용자는 이 후보 중 하나만 고를 수 있다. 새 box 그리기, 자유 mask 편집, 특정 구간만 다른 ID로 바꾸기는 없다.
- 선택을 바꾸면 그 ID의 trajectory로 crop 계획부터 다시 만든다. 가려짐 뒤 다른 ID로 자동 치환하지 않으며, 그 결과의 낮은 coverage·clipped는 그대로 표시한다.
- 후보가 0개면 선택 기능 대신 "추적 대상 없음 — 중앙 crop, degraded"를 표시한다.

| 설명 note | 텍스트 수정(고위험 주장의 explicit 근거 추가 포함) | 입력 변경으로 보고 이해 단계부터 재실행 | 6개 |
| 원본 영상 | 웹에서 교체하지 않음 | 새 job | — |

- 길이는 SC-006 규칙으로 계산한다. 포함된 유효 구간이 하나 이상이면 시간순으로 이어 붙이고, 28초를 넘으면 뒤쪽을 자르고, 6초에 못 미치면 원본 반복(padding)으로 채운다. 이 계산을 거친 본 영상은 6~28초이고 카드 2초가 더해진다. 따라서 선택 구간 합이 6초 미만이라는 이유만으로 거부하지 않는다(3초 원본도 padding 가능). 적용 전에 막는 경우는 포함된 유효 구간이 없을 때, 원본 길이 밖이거나 새 겹침이 생기는 경계를 입력했을 때뿐이다. [SC-006]
- 설명 note 수정으로 이해 단계가 다시 돌면 이전 revision에서 손으로 고친 문구를 자동 병합하지 않는다. 이전 문구는 비교용으로만 보여 준다.
- 적용은 명시적 POST이며 서버는 revision 증가와 승인 무효화를 먼저 기록한 뒤 재계산한다. 재계산 결과물만 새 revision에 붙는다. [SC-005]
- "되돌리기"는 아직 적용하지 않은 초안을 버리는 동작으로만 둔다. 저장된 revision을 이전 revision으로 되돌리는 UI는 만들지 않는다.

### 4.5 6개 미리보기와 안전 영역

- 3비율×훅 A/B를 한 구역에 나란히 두고, 9:16 A/B 두 개를 "게시 대상", 나머지 4개를 "다운로드 전용"으로 표시한다.
- 원본 대응 재생은 4.1처럼 선택한 결과 1개를 대상으로 한다. 여러 결과를 동시에 재생하는 선택지는 두지 않는다.
- 각 결과에 안전 영역 겹쳐 보기를 둔다. 9:16은 루트 값(위 14%, 아래 22%)을 쓰되 "[미확인] 잠정값"이라고 표시한다. 다른 비율의 안전 영역 값은 원본에 없으므로 임의 값을 표시하지 않는다.
- 각 결과 카드: 길이, 상태(완료/렌더 중/실패/이전 revision), 경고(degraded, clipped, safe_area_violation, Image 대체, 정책 warn/block), 다운로드.

### 4.6 표시하는 수치와 표시하지 않는 수치

| 표시한다(원본·산출물에서 계산 가능) | 표시하지 않는다 |
| --- | --- |
| 보간 전 coverage, clipped 프레임 수, safe_area_violation 프레임 수 | 종합 "광고 품질 점수", 예상 CTR·전환율·성과 |
| 정책 flag와 규칙 ID, 근거 종류별 개수, 근거 없는 문구 수 | 근거 없이 모델이 매긴 매력도·추천 점수 |
| Image 대체 여부, 렌더 frame hash, 실행 모드 | 결측 confidence를 채운 값 |

모델이 confidence를 반환한 경우에만 원값과 출처를 보이며, 품질 판정의 대체로 쓰지 않는다.

### 4.7 dirty·stale 처리

- **dirty:** 적용하지 않은 편집은 브라우저 안의 초안이다. 서버 상태가 아니며 승인·다운로드·게시 대상에 포함되지 않는다. dirty 상태에서는 승인 버튼을 막고 "미적용 편집 n개"를 표시한다. 초안을 버리면 마지막으로 저장된 revision 상태로 돌아간다. 페이지 이탈·job 전환 시 경고한다.
- **stale:** 새 revision 재렌더 중에는 이전 revision 결과를 비교용으로 재생할 수 있지만 "이전 revision n — 승인·게시 불가"로 표시한다. 새 revision은 6개가 모두 commit되어야 승인 가능해진다. 일부만 끝난 상태로 승인하지 않는다(BA-13).
- **동시 수정:** CLI 등에서 revision이 바뀐 뒤 웹이 적용·승인을 보내면 서버가 stale revision으로 거부한다. 화면은 최신 상태를 다시 불러오고, 사용자의 미적용 초안과 바뀐 내용을 함께 보여 준다(BA-03).
- 렌더·게시가 진행 중인 job에는 편집을 받지 않는다. 편집 컨트롤은 읽기 전용으로 바뀌고 이유를 표시한다.

## 5. 단계 3 — 승인·내보내기

### 5.1 승인

승인 버튼은 아래 조건을 모두 만족할 때만 활성화하고, 막힌 조건은 항목별로 보인다.

- 현재 revision의 6개 결과가 모두 commit되어 있다.
- 정책 block이 없고, explicit 근거 없는 고위험 주장이 없다.
- 검토 필수 주장(`ClaimReview`) 중 pending이나 rejected가 없다.
- 미적용 편집이 없고, 화면의 revision과 서버 revision이 같다.
- warn·degraded·clipped·Image 대체는 승인을 막지 않지만 승인 화면에 다시 나열하고 승인 기록에 포함한다.

승인은 명시적 POST이며 revision과 content digest를 기록한다. digest에는 6개 결과, 게시 영상·썸네일, 문구·CTA·destination, 계정·Page, 예산·통화·국가, 정책 결과·경고, `EvidenceRef`·`ClaimReview`, 선택 object, 사용 구간이 들어간다(implementation-contracts §4). 페이지 로드, 미리보기, 모델 응답은 승인을 만들지 않는다. [SC-003·012]

### 5.2 다운로드

- 현재 revision의 결과 6개는 승인 전에도 개별 파일로 내려받을 수 있다. 파일 이름·digest·revision·승인 여부를 담은 manifest를 함께 받을 수 있다.
- 다운로드는 승인이 아니며 승인을 요구하지도 않는다. 승인이 필요한 것은 실제 게시뿐이다. 미승인 revision에서 받은 파일은 manifest에 미승인으로 기록한다.
- 렌더가 끝나지 않았거나 실패한 결과는 다운로드 링크를 만들지 않는다.

### 5.3 PAUSED 게시

- 게시는 승인과 분리된 별도 버튼이다. 게시 전에 승인 digest와 현재 내용이 같은지 서버가 다시 검사하고, 다르면 외부 요청 없이 거부한다(BA-01).
- live job의 실제 게시 활성화 조건: Marketing 자격, H3 사람 gate 승인, destination 등 필수 값. 빠진 조건을 표시하고 비활성화한다. fixture job의 mock 게시에는 실제 자격·H3를 요구하지 않되 동일한 로컬 검토·승인 조건을 적용한다.
- fixture 모드의 게시는 mock 게시이며 결과에 "실제 광고 없음"을 표시한다. replay 모드에서는 게시를 제공하지 않는다.
- 확인 단계에서 대상 계정·Page, 일 예산·통화, 게시할 9:16 A/B, "모든 캠페인·광고 세트·광고는 PAUSED로 생성되며 활성화하지 않음"을 보여 준다.
- 진행 표시는 원격 리소스 단위(영상 2, 썸네일, 소재 2, 캠페인, 광고 세트, 광고 2)로 하며 각 항목을 `CONFIRMED`/`FAILED`/`UNKNOWN`으로 표시한다. [SC-004]
- **결과 불명:** 생성 요청을 보낸 뒤의 응답 유실·timeout은 "생성 여부 불명"(`UNKNOWN`)이다. "생성되지 않음"으로 표시하지 않고 자동 재전송하지 않는다. 원격 조회 또는 운영자 대조로 확인할 때까지 이어서 진행하지 않는다(BA-04).
- **부분 실패:** 확정된 ID는 재사용하고 누락된 단계만 이어서 진행한다(AC-17, BA-05).
- **완료:** read-back으로 확인한 원격 ID, configured status(PAUSED), effective status, 확인 시각을 보여 준다. 두 status가 다를 수 있음을 함께 표시한다(BA-14). 이 결과는 Meta 광고 심사 통과를 뜻하지 않는다.
- 게시 시작 뒤의 취소는 다음 리소스 요청을 보내지 않겠다는 요청일 뿐이다. 이미 보냈거나 보내는 중이던 요청은 원격 생성이 없었다고 간주하지 않으며, 응답을 확정하지 못한 리소스는 `UNKNOWN` 확인 경로로 보낸다.
- 게시 후 내용 변경은 새 job으로 시작한다. 기존 원격 객체를 자동 수정·활성화하지 않으며 같은 job의 게시 revision fork는 제공하지 않는다.

## 7. 접근성·조작 기준

- 모든 행동은 키보드로 가능하고, 재생·seek·근거 이동 후 초점 위치가 예측 가능해야 한다.
- 경고·근거 종류·상태를 색만으로 구분하지 않고 문자 라벨을 함께 쓴다.
- 미리보기 재생 중에도 자막·훅 문구를 텍스트로 확인할 수 있게 한다.
- 이 기준은 의미 수준이며, 실제 화면은 구현 후 렌더 상태에서 확인해야 한다.

## 11. 시연 경로

1. 저장된 작업 또는 새 작업을 열고 실행 모드와 provider 준비 상태를 확인한다.
2. 결과 하나를 재생하며 원본이 대응 시점으로 따라가는지, 엔드카드가 합성 layer로 표시되는지 본다.
3. 카피 근거를 눌러 설명 문구 범위와 영상 시점으로 이동하고, 근거 없는 고위험 문구가 승인을 막는지 확인한다.
4. 물체 후보를 바꾸거나 구간·자막을 고쳐 영향 요약→재렌더→이전 승인 무효화를 확인한다.
5. 6개 결과와 안전 영역을 확인하고 현재 revision을 승인한다.
6. live·H3 조건이 충족된 경우에만 9:16 A/B를 게시하고, 테스트 계정에서 PAUSED 상태와 소재를 대조한다.

fixture·replay 시연은 로컬 처리와 상태 흐름의 증거다. 실제 모델 결과, 광고 계정 생성, 플랫폼 심사 통과, 광고 성과는 증명하지 않는다. 렌더 시간·요청 수·비용은 실측한 경우에만 기록한다.
